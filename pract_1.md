# Технологии тестирования программных продуктов

## Практическая работа: от новой сборки к smoke-чек-листу

> Продолжительность: 2 академических часа.  
> Результат: командный smoke-чек-лист из 15–20 проверок для выбранного сайта.

Представьте обычную ситуацию в команде разработки. Вчера программисты закончили новую версию продукта, а сегодня сообщили, что её можно тестировать. Полная проверка займёт много времени, однако сначала нужно ответить на более простой вопрос: **работает ли продукт хотя бы на базовом уровне и есть ли смысл переходить к подробному тестированию?**

Именно с этого вопроса начинается занятие. Сначала мы разберём, как устроена осмысленная проверка, затем пройдём основной пользовательский маршрут российского интернет-магазина и постепенно превратим свои наблюдения в чек-лист. После общего разбора вы продолжите работу в командах по четыре человека.

---

## Зачем разработчику разбираться в тестировании

Разработать функцию недостаточно. Команда должна понимать, соответствует ли продукт требованиям, работают ли основные сценарии и не сломали ли изменения уже существующее поведение.

Тестирование не доказывает, что ошибок в системе совсем нет. Оно даёт информацию о состоянии продукта и связанных с выпуском рисках. На основании этой информации команда решает, можно ли продолжать работу со сборкой, выпускать её пользователям или сначала нужно исправить критические проблемы.

В течение курса эта идея будет рассматриваться с разных сторон. Мы начнём с ручного тестирования и тестовой документации, а затем перейдём к техническим уровням и инструментам.

| Направление | Что будет рассматриваться |
|---|---|
| Основные понятия | тестирование, валидация, верификация, дефекты |
| Документация | чек-листы, требования, баг-репорты, тест-планы |
| Уровни тестирования | модульное, интеграционное и системное тестирование |
| Нефункциональные проверки | производительность, нагрузка и безопасность |
| Инструменты | Qt/QTestLib, JMeter, средства проверки веб-приложений |
| Автоматизация | Selenium IDE / WebDriver и автоматизированные сценарии |

Главную мысль курса можно сформулировать так:

> Разработка отвечает на вопрос «как создать продукт?», а тестирование — «откуда мы знаем, что он работает так, как должен?»

Чтобы ответить на второй вопрос, недостаточно просто так нажимать на кнопки. Нужна проверка, результат которой можно объяснить и повторить.

## От действия к результату проверки

В основе любой проверки лежит сравнение ожидаемого и фактического поведения.

```text
Условие → действие → ожидаемый результат → фактический результат → вывод
```

Например, пользователь открыл карточку компьютерной мыши и нажал кнопку «Купить» или «В корзину».

```text
Условие: открыта карточка товара.
Действие: добавить товар в корзину.
Ожидаемый результат: товар появляется в корзине.
Фактический результат: товар появился в корзине.
Вывод: проверка пройдена — Pass.
```

Если после того же действия корзина осталась пустой, ожидаемое и фактическое поведение не совпали. Такая проверка получает статус `Fail`.

`Fail` не означает, что тестировщик плохо выполнил работу. Наоборот, проверка обнаружила несоответствие. Дальше нужно выяснить, является ли оно дефектом продукта, особенностью требований или ошибкой в самой проверке.

Ожидаемый результат тоже нельзя придумывать произвольно. Его источником могут быть требования, пользовательская история, техническое задание, макет, бизнес-правило или явно согласованное поведение. Если ожидание нигде не определено, это нужно отметить и уточнить.

Теперь можно перейти к вопросу о том, какие проверки выполнять первыми.

## Почему подробное тестирование начинается со smoke-проверки

Допустим, интернет-магазин только что обновили. Можно сразу проверять десятки фильтров, разные разрешения экрана и редкие ошибки ввода. Но вся эта работа теряет смысл, если магазин вообще не открывается, поиск не возвращает товары, карточки недоступны или корзина не работает.

Поэтому сначала выполняют короткий набор самых важных проверок.

> **Smoke-тестирование** — быстрый минимальный набор проверок критически важных функций продукта. Его цель — понять, пригодна ли сборка для дальнейшего тестирования.

Это похоже на подготовку автомобиля к дальней поездке. Водитель не разбирает двигатель целиком, а сначала проверяет, заводится ли машина, работают ли тормоза и есть ли топливо. Если автомобиль не заводится, обсуждать удобство кресел пока рано.

Для интернет-магазина основной маршрут обычно выглядит так:

```text
Открыть сайт
    ↓
Найти нужный товар
    ↓
Открыть карточку товара
    ↓
Добавить товар в корзину
    ↓
Перейти к оформлению заказа
```

Дополнительными критическими функциями могут быть выбор региона, авторизация, изменение количества товара и удаление товара из корзины.

При этом не каждая обнаруженная ошибка блокирует сборку. Небольшой визуальный дефект может быть важен, но обычно не мешает продолжить тестирование. Невозможность найти товар или добавить его в корзину напрямую разрушает основной сценарий магазина.

Хороший smoke-набор остаётся коротким, быстро выполняется и сосредоточен на функциях, без которых продукт теряет основную ценность.

## Проходим маршрут покупателя на сайте DNS

Для общего разбора используем российский интернет-магазин цифровой и бытовой техники **DNS**:

<https://www.dns-shop.ru/>

Начнём тестирование с главной страницы. На ней должны быть доступны основные точки входа: **«Каталог»**, поле **«Поиск по сайту»**, **«Сравнение»**, **«Избранное»** и **«Корзина»**. Уже из этого набора можно выделить логические разделы будущего чек-листа.

Сначала убедимся, что главная страница открывается и основные элементы интерфейса доступны. Затем введём в поле «Поиск по сайту» запрос, например `беспроводная мышь`. После отправки запроса пользователь ожидает увидеть товары, соответствующие введённой фразе.

Откроем один из найденных товаров. В карточке должны быть понятны как минимум:

- название товара;
- цена;
- основные характеристики;
- сведения о наличии или способах получения;
- действие для добавления товара в корзину.

После добавления товара откройте раздел «Корзина». Проверьте, что выбранный товар действительно появился, его название и цена совпадают с карточкой, а итоговая сумма рассчитана понятно.

На этом граница общего исследования проходит перед необратимыми действиями. Можно открыть следующий шаг оформления и посмотреть, что он доступен, но нельзя подтверждать реальный заказ, бронирование или оплату.

В результате получается не случайный набор кликов, а связный пользовательский маршрут, каждый переход которого можно превратить в отдельную проверку:

- главная страница успешно открывается;
- поиск существующего товара возвращает релевантные результаты;
- карточка выбранного товара открывается;
- товар добавляется в корзину;
- добавленный товар отображается с корректной ценой;
- из корзины доступен переход к оформлению заказа.

Пока мы только формулируем проверки. Статусы `Pass/Fail` будут заполняться при выполнении чек-листа на следующем занятии.

## Как наблюдения превращаются в чек-лист

Чек-лист — это краткий список того, **что необходимо проверить**.

```text
Выбранный товар добавляется в корзину.
```

Здесь нет подробных шагов, потому что предполагается, что исполнитель уже знаком с интерфейсом продукта. Если нужно точно зафиксировать предусловия, действия и ожидаемый результат, используется тест-кейс.

```text
Название: добавление одного товара в пустую корзину

Предусловия:
- корзина пуста;
- открыта карточка товара.

Шаги:
1. Нажать кнопку добавления товара в корзину.
2. Открыть раздел «Корзина».

Ожидаемый результат:
- выбранный товар отображается в корзине;
- количество товара равно 1;
- цена совпадает с ценой в карточке.
```

Таким образом, чек-лист отвечает на вопрос «что проверить?», а тест-кейс подробно объясняет, «при каких условиях, какими действиями и с каким ожидаемым результатом» проводится проверка.

| Чек-лист | Тест-кейс |
|---|---|
| Краткая формулировка | Подробное описание |
| Быстро составлять и обновлять | Требует больше времени на подготовку |
| Допускает некоторую интерпретацию | Обеспечивает более точную повторяемость |
| Подходит для знакомого продукта и быстрых прогонов | Подходит для сложных или строго регламентированных сценариев |

На этой практике нужен именно чек-лист.

## Как написать проверку, которую поймёт другой человек

Главное правило простое:

> **Один пункт чек-листа — одна понятная и наблюдаемая проверка.**

Формулировка «проверить магазин» не подходит, потому что непонятно, что именно нужно сделать и какой результат считать успешным. Формулировка «корзина работает корректно» тоже слишком широкая: в ней скрываются добавление, удаление, изменение количества и расчёт суммы.

Удобно строить пункт по формуле:

```text
[объект] + [наблюдаемое поведение] + [условие, если оно важно]
```

| Неудачная формулировка | Почему она не подходит | Улучшенный вариант |
|---|---|---|
| Проверить сайт | Не указан объект проверки | Главная страница успешно открывается |
| Проверить поиск | Не определён результат | Поиск существующего товара возвращает релевантные результаты |
| Корзина работает корректно | Слишком много поведения в одной строке | Выбранный товар добавляется в корзину |
| Проверить кнопки, ссылки и изображения | Объединено несколько проверок | Разделить элементы на отдельные пункты |
| Нажать «Войти» | Описано действие, но не ожидание | Форма авторизации открывается по кнопке «Войти» |
| Страница загружается быстро | Слово «быстро» неоднозначно | Страница становится доступна не более чем за согласованное время |

Перед добавлением пункта в smoke-набор полезно спросить: связан ли он с основной ценностью продукта, помешает ли его падение пройти главный маршрут и нужен ли результат для решения о дальнейшем тестировании? Эти вопросы не дают smoke-чек-листу превратиться в полный список всех возможных проверок.

## Практическая работа

Теперь разбейтесь на команды **по 4 человека**. Каждая команда выбирает один российский интернет-магазин и составляет для него общий smoke-чек-лист из 15–20 пунктов.

### Задача команды

Сначала запишите название и адрес магазина, одним предложением сформулируйте его назначение, и затем опишите основной пользовательский маршрут. 

После этого разделите сайт на логические области (каталог, поиск, карточки т.д.) и составьте для каждой несколько критических проверок.

Минимально стоит рассмотреть доступность главной страницы, навигацию, выбор региона, каталог, поиск или фильтры, карточку товара, корзину, начало оформления и понятную обработку хотя бы одной пустой или ошибочной ситуации.

Пример начала таблицы:

| № | Раздел | Проверка | Статус | Примечание |
|---:|---|---|---|---|
| 1 | Доступность | Главная страница успешно открывается |  |  |
| 2 | Каталог | Каталог товаров открывается |  |  |
| 3 | Поиск | Поиск существующего товара возвращает релевантные результаты |  |  |
| 4 | Карточка товара | Карточка выбранного товара открывается |  |  |
| 5 | Корзина | Выбранный товар добавляется в корзину |  |  |

Формат сдачи: Документ (Google Docs / Word / Markdown) с чек-листом.
Команда сдаёт один документ в Markdown, Google Docs или Microsoft Word.

Критерии оценки:
1. [ ] Полнота покрытия критического функционала
2. [ ] Чёткость и лаконичность формулировок
3. [ ] Логическая структура (группировка по разделам)
4. [ ] Наличие не менее 15 пунктов
